## Introduction

Hetzner dedicated servers are a good place to run a single-node OpenShift (SNO) lab. You get plenty of CPU, memory, and fast local NVMe storage, and the monthly cost is predictable. The awkward part is the install. On a dedicated server in Robot, you do not get the same easy ISO boot workflow you have with a VM or with Hetzner Cloud. OpenShift normally expects either a discovery ISO or PXE boot, and neither is especially convenient here.

The approach in this tutorial is to use the Hetzner [Rescue System](https://docs.hetzner.com/robot/dedicated-server/troubleshooting/hetzner-rescue-system/) as a temporary working environment. Once the server is in rescue mode, you can build the OpenShift Agent-based Installer PXE artifacts there and then use `kexec` to jump straight into the Red Hat CoreOS (RHCOS) installer kernel.

I cover the manual path first and keep every command in the article so you can see exactly what is happening. There is also an optional shortcut for the preparation steps. The goal is:

- A running single-node OpenShift cluster on one Hetzner dedicated server.
- A `kubeconfig` and `kubeadmin` password saved on your workstation.
- A Robot firewall configured before the installer boots.

This setup is intended for labs and testing. A single-node cluster is a single point of failure, and `kexec` can behave differently from a full reboot on different hardware. Use a [KVM console](https://docs.hetzner.com/robot/dedicated-server/maintenance/kvm-console/) when diagnosing boot problems. For the standard installation procedure, use the [Agent-based Installer documentation](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/installing_an_on-premise_cluster_with_the_agent-based_installer/index).

> **Validation status of this revision:** the original workflow was developed on an EX44. The revised commands have offline regression checks, but a fresh end-to-end hardware test, including browser OAuth login, is still required. Troubleshooting below is not a confirmed diagnosis of the previously reported login failure.

**Prerequisites**

- **An x86_64 Hetzner dedicated server** that you can boot into Linux rescue and erase. Check the [requirements for your OpenShift release](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/installing_on_a_single_node/preparing-to-install-sno), including CPU features, memory, storage, and boot mode. The documented SNO minimums are 8 vCPUs, 16 GB RAM, and 120 GB disk; leave additional capacity for workloads.
- **A Red Hat account and pull secret** from the [Red Hat console](https://console.redhat.com/openshift/install/pull-secret). Confirm the subscription or evaluation terms that apply to your intended use; this tutorial does not establish entitlement or support coverage.
- **An SSH key pair.** Put only the workstation's public key on the rescue host, for example in `/root/.ssh/workstation.pub`. Keep the private key on your workstation.
- **An exact OpenShift GA patch release.** The `agent create pxe-files` command is documented from [OpenShift 4.14](https://docs.redhat.com/en/documentation/openshift_container_platform/4.14/html/installing_an_on-premise_cluster_with_the_agent-based_installer/prepare-pxe-assets-agent). That is a feature minimum, not a tested compatibility matrix. Select an available, supported release from the [Red Hat mirror](https://mirror.openshift.com/pub/openshift-v4/x86_64/clients/ocp/), and use matching installer and client binaries.
- **Working DNS and an IPv4-only, directly connected primary NIC.** Set up the records below before generating the installer. Bonding, VLANs, IPv6, and gateways outside the configured subnet require additional network configuration and are outside this example.
- **A workstation with Bash, SSH, `scp`, `dig`, Python 3, and a version-matched `oc` client**, and familiarity with SSH, Robot, and YAML.

**Example terminology**

Replace every placeholder with your own value. The example server addresses are documentation-only; they are not usable addresses for an actual installation.

| Placeholder | Example | Meaning |
| ----------- | ------- | ------- |
| `<server-ip>` | `203.0.113.45` | Server's public IPv4 |
| `<prefix>` | `26` | Actual IPv4 prefix length |
| `<machine-cidr>` | `203.0.113.0/26` | Network calculated from the server IPv4/prefix |
| `<gateway>` | `203.0.113.1` | Actual default gateway |
| `<interface>` | `enp41s0` | Primary NIC name in rescue |
| `<mac>` | `a8:a1:59:b3:c2:01` | NIC MAC address |
| `<dns>` / `<dns2>` | `185.12.64.1` / `185.12.64.2` | Actual Hetzner recursive resolvers; see Step 3 |
| `<disk-id>` | Select from `/dev/disk/by-id/` | Whole-disk identifier, not a `-partN` entry |
| `<disk-serial>` | `S63CNF0X212063` | Install disk serial |
| `<your-admin-ip>` | `203.0.113.10/32` | Workstation's public IP/CIDR |
| `<base-domain>` | `example.com` | Base domain |
| `<cluster-name>` | `sno` | Cluster name |
| `<ocp-version>` | An exact `4.y.z` release | Use the selected release consistently |

`<cluster-name>` and `<base-domain>` are separate fields: `sno` and `example.com` produce `api.sno.example.com`.

Configure these DNS records to point to `<server-ip>` for this one-node layout:

| Record | Example |
| ------ | ------- |
| Node hostname | `sno.example.com` |
| API | `api.sno.example.com` |
| Internal API | `api-int.sno.example.com` |
| Application wildcard | `*.apps.sno.example.com` |

The wildcard covers both `console-openshift-console.apps.sno.example.com` and `oauth-openshift.apps.sno.example.com`, as well as application routes. Avoid a catch-all parent wildcard such as `*.example.com` for this installation; it can interfere with installer DNS validation. Do not remove the required `*.apps.sno.example.com` wildcard.

Public DNS is not mandatory, but the chosen resolvers must answer these names from the rescue host, the installed node/cluster, and the administration workstation. Private or split DNS is valid only when those clients can reach the correct resolvers. Workstation-only `/etc/hosts` entries do **not** replace cluster-side DNS. See Red Hat's [SNO DNS requirements](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/installing_on_a_single_node/preparing-to-install-sno).

## Step 1 - Lock down the Robot firewall first

Configure the firewall **before** booting the installer. The node will use a public IP.

The [Robot firewall](https://docs.hetzner.com/robot/dedicated-server/firewall/) is stateless: rules match individual packets, not tracked connections. Rules run from top to bottom; unmatched packets are dropped. Enter the admin and return-traffic rules before activating the firewall so that you do not lock yourself out.

In Robot, open your server's **Firewall** tab. Enable **Filter IPv6 packets** and **Hetzner Services**. Set **IP version = IPv4 explicitly on every rule below**. With IPv6 filtering enabled and no IPv6 allow rules, IPv6 is blocked except for the ICMPv6 traffic Hetzner always permits.

**Outgoing:**

| # | Name | IP version | Protocol | Action |
| - | ---- | ---------- | -------- | ------ |
| 1 | Allow outgoing IPv4 | IPv4 | `*` | accept |

**Incoming:**

Run `curl -4 https://ip.hetzner.com` on your workstation to find the public admin IP. Retain any additional rules required for your existing vSwitch or management setup.

| # | Name | IP version | Source IP | Destination port | Protocol | TCP flags | Action |
| - | ---- | ---------- | --------- | ---------------- | -------- | --------- | ------ |
| 1 | Trusted admin | IPv4 | `<your-admin-ip>` | | `*` | | accept |
| 2 | ICMP | IPv4 | | | icmp | | accept |
| 3 | TCP return packets | IPv4 | | 32768-65535 | tcp | ack | accept |
| 4 | UDP high ports | IPv4 | | 32768-65535 | udp | | accept |

Rule 1 permits SSH, API, and console access from your admin IP. Rule 3 follows Hetzner's documented TCP return-traffic pattern. Rule 4 is a lab trade-off: it allows **any UDP packet** to that port range, not just responses. Review it before exposing additional services; it overlaps the high end of the usual NodePort range. More restrictive UDP rules require accounting for your actual DNS, NTP, and other UDP traffic.

Hetzner allows 10 rules per direction and documents an application delay of approximately 20-30 seconds. Confirm that a new SSH connection works after the rules are active. The selected ephemeral range must also cover the source ports used by the node's outgoing connections.

## Step 2 - Boot rescue and select the install disk

Enable the 64-bit Linux Rescue System in Robot and reboot into it. The commands below target a Debian-based x86_64 rescue environment. Record its actual version rather than assuming it is unchanged:

```bash
ssh root@<server-ip>
cat /etc/os-release
uname -r
lsblk -o NAME,SIZE,TYPE,MODEL,SERIAL,MOUNTPOINTS
ls -l /dev/disk/by-id/
```

**Warning: the selected disk will be overwritten by installation. Back up its data first.** Select a whole-disk `/dev/disk/by-id/` entry and record its serial. Do not select a partition or an unrelated data disk. NVMe names such as `nvme0n1` can change across boots; use the same serial in the installer configuration.

```bash
export INSTALL_DISK='/dev/disk/by-id/<disk-id>'
export DISK_SERIAL='<disk-serial>'
```

For a reused disk that needs its existing signatures removed, inspect it and confirm the serial before wiping. Stop if it is mounted, used as swap, or part of an active RAID/LVM stack; do not force a wipe of an in-use device. `wipefs` removes signatures, not all data or all possible RAID/LVM metadata.

```bash
(
  set -euo pipefail
  [[ -b "$INSTALL_DISK" ]] || { echo 'Not a block device' >&2; exit 1; }
  [[ $(lsblk -dn -o TYPE "$INSTALL_DISK") == disk ]] || exit 1
  actual_serial=$(lsblk -dn -o SERIAL "$INSTALL_DISK" | xargs)
  [[ -n "$DISK_SERIAL" && "$actual_serial" == "$DISK_SERIAL" ]] || {
    echo 'Disk serial mismatch; nothing erased' >&2; exit 1;
  }
  lsblk -o NAME,SIZE,TYPE,SERIAL,MOUNTPOINTS "$INSTALL_DISK"
  [[ -z $(lsblk -nr -o MOUNTPOINTS "$INSTALL_DISK" | sed '/^[[:space:]]*$/d') ]] || {
    echo 'A disk or child device is mounted/in use; stop here' >&2; exit 1;
  }
  wipefs --no-act "$INSTALL_DISK"
  read -r -p 'Type the disk serial to remove its signatures: ' confirmation
  [[ "$confirmation" == "$DISK_SERIAL" ]] || { echo 'Cancelled'; exit 1; }
  wipefs --all "$INSTALL_DISK"
)
```

Use Bash for the remaining rescue commands. Blocks enclosed in parentheses run in a subshell with error handling; a failed command stops that block without closing your SSH shell. **Do not continue to the next step after an error.**

## Step 3 - Collect network facts and check DNS

Read the primary interface, IPv4/prefix, default gateway, and MAC from the live rescue system:

```bash
ip -brief -4 addr show
ip -4 route show
cat /sys/class/net/<interface>/address
```

Use the actual routing configuration. This example assumes that the gateway is in the configured IPv4 subnet. A `/32` address with a separate on-link gateway route is not equivalent to the simple route example in Step 5; do not guess a different prefix to make it fit.

Hetzner's [recursive resolvers](https://docs.hetzner.com/robot/dedicated-server/general-information/recursive-name-servers/) are `185.12.64.1` and `185.12.64.2`, reachable from Hetzner data centers. For private DNS, use your own reachable resolvers that serve the cluster zone instead. Do not bake a loopback stub such as `127.0.0.53` into the node configuration.

To inspect the current resolver setup, use `resolvectl status '<interface>'` when available. Treat `/etc/resolv.conf` as information about the current rescue session, not automatically as the final node's resolver configuration.

Install the common preparation utilities before either path. The `kexec-tools` preseed disables the older Debian package's automatic kexec-on-reboot option; the final boot is explicit. Newer Debian packages removed that option, as described in the [package changelog](https://sources.debian.org/src/kexec-tools/1%3A2.0.29-2/debian/changelog/).

```bash
(
  set -euo pipefail
  apt-get update
  printf '%s\n' \
    'kexec-tools kexec-tools/use_grub_config boolean false' \
    'kexec-tools kexec-tools/load_kexec boolean false' | debconf-set-selections
  apt-get install -y ca-certificates curl dnsutils git python3 kexec-tools
)
```

Set these values once in the rescue shell. Replace the placeholders, and use the same values in both YAML files later:

```bash
export SERVER_IP='<server-ip>'
export IP_WITH_PREFIX='<server-ip>/<prefix>'
export INTERFACE='<interface>'
export GATEWAY='<gateway>'
export BASE_DOMAIN='<base-domain>'
export CLUSTER_NAME='<cluster-name>'
export OCP_VERSION='<ocp-version>'
export DNS1='185.12.64.1'
export DNS2='185.12.64.2'
export NODE_HOSTNAME="$CLUSTER_NAME.$BASE_DOMAIN"
```

Calculate the machine network without nested shell quoting. Copy the resulting network into `<machine-cidr>` in Step 5:

```bash
python3 - "$IP_WITH_PREFIX" <<'PY'
import ipaddress
import sys

interface = ipaddress.ip_interface(sys.argv[1])
if interface.version != 4:
    raise SystemExit("This example requires an IPv4 interface")
print(f"Server IPv4: {interface.ip}")
print(f"Machine network: {interface.network}")
PY
```

Run the following DNS preflight **from rescue**, against **both resolvers that will be placed in `agent-config.yaml`**. It checks the node, API, internal API, console, OAuth, and a fresh application name. For this IPv4-only example, it rejects unexpected AAAA answers as well as absent or incorrect A answers.

```bash
(
  set -euo pipefail
  : "${SERVER_IP:?}" "${DNS1:?}" "${DNS2:?}" "${CLUSTER_NAME:?}" "${BASE_DOMAIN:?}"
  zone="$CLUSTER_NAME.$BASE_DOMAIN"
  for dns in "$DNS1" "$DNS2"; do
    for host in "$zone" "api.$zone" "api-int.$zone" \
      "console-openshift-console.apps.$zone" "oauth-openshift.apps.$zone" \
      "preflight-${RANDOM}-${RANDOM}.apps.$zone"; do
      answer=$(dig +time=3 +tries=1 +noall +answer "@$dns" "$host" A |
        awk '$4 == "A" {print $5}' | sort -u)
      [[ "$answer" == "$SERVER_IP" ]] || {
        printf 'DNS mismatch: %s via %s returned [%s], expected %s\n' \
          "$host" "$dns" "$answer" "$SERVER_IP" >&2
        exit 1
      }
      ipv6=$(dig +time=3 +tries=1 +noall +answer "@$dns" "$host" AAAA |
        awk '$4 == "AAAA" {print $5}')
      [[ -z "$ipv6" ]] || {
        printf 'Unexpected AAAA answer for IPv4-only host %s: %s\n' "$host" "$ipv6" >&2
        exit 1
      }
      printf 'OK: %s via %s\n' "$host" "$dns"
    done
  done
)
```

Also verify the real API, console, and OAuth names using the workstation's normal resolver before continuing. Do not use the Hetzner-only resolver addresses from outside its network. A browser using a different secure-DNS service may see different answers. A working rescue preflight does not establish that DNS will work from inside the installed cluster; Step 9 checks that separately.

## Step 4 - Install the toolchain in rescue

The manual path needs matching `oc` and `openshift-install` binaries, `nmstatectl` for network configuration, and the `kexec-tools` already installed in Step 3.

### Download and verify oc and openshift-install

The block below uses a new temporary directory for every attempt. It requires exactly one checksum entry for **each** expected archive, checks both archives before extracting either, and stops on a download, verification, or extraction failure. Checksums fetched over the same HTTPS channel detect corruption; this is not an independent signature-verification procedure.

```bash
(
  set -euo pipefail
  VER="${OCP_VERSION:?Set the exact OpenShift release in Step 3}"
  [[ "$VER" =~ ^4\.[0-9]+\.[0-9]+$ ]] || {
    echo 'Select an exact GA patch version, not latest or a placeholder' >&2; exit 1;
  }
  BASE=https://mirror.openshift.com/pub/openshift-v4/x86_64/clients/ocp/${VER}
  work=$(mktemp -d)
  trap 'rm -rf "$work"' EXIT
  cd "$work"
  archives=(openshift-client-linux.tar.gz openshift-install-linux.tar.gz)
  for file in "${archives[@]}" sha256sum.txt; do
    curl --proto '=https' --proto-redir '=https' --tlsv1.2 \
      --fail --location --retry 3 --output "$file" "$BASE/$file"
    test -s "$file"
  done
  for file in "${archives[@]}"; do
    expected=$(awk -v file="$file" '$2 == file || $2 == "*" file {print $1}' sha256sum.txt)
    [[ "$expected" =~ ^[[:xdigit:]]{64}$ ]] || {
      printf 'Missing, duplicate, or invalid checksum for %s\n' "$file" >&2; exit 1;
    }
    printf '%s  %s\n' "$expected" "$file" >> required.sha256
  done
  sha256sum --strict --check required.sha256
  mkdir stage
  tar -xzf openshift-client-linux.tar.gz -C stage oc kubectl
  tar -xzf openshift-install-linux.tar.gz -C stage openshift-install
  install -m 0755 stage/oc stage/kubectl stage/openshift-install /usr/local/bin/
  oc version --client
  openshift-install version
)
```

Record the reported versions for the hardware test. A nonexistent release or missing archive must stop preparation, not trigger an implicit fallback to another release.

## Step 5 - Write the install and agent configs

The Agent-based Installer reads two YAML files. Keep backups because asset generation consumes them. These are YAML templates, **not** shell heredocs: replace the angle-bracket placeholders yourself using the verified values from Step 3.

```bash
umask 077
install -d -m 0700 /root/ocp-prepare/install
```

Create `/root/ocp-prepare/install/install-config.yaml`. Use one control-plane replica, zero compute replicas, and `platform: none`. Paste the pull secret JSON as a single-quoted value and your SSH **public** key:

```yaml
apiVersion: v1
baseDomain: <base-domain>
metadata:
  name: <cluster-name>
compute:
- name: worker
  replicas: 0
controlPlane:
  name: master
  replicas: 1
networking:
  networkType: OVNKubernetes
  clusterNetwork:
  - cidr: 10.128.0.0/14
    hostPrefix: 23
  serviceNetwork:
  - 172.30.0.0/16
  machineNetwork:
  - cidr: <machine-cidr>
platform:
  none: {}
pullSecret: '<paste-pull-secret-json-here>'
sshKey: |
  ssh-ed25519 AAAA... your-public-key
```

The cluster and service networks must not overlap your physical or management networks. `<machine-cidr>` is the calculated network, for example `203.0.113.0/26`, not the host address.

Create `/root/ocp-prepare/install/agent-config.yaml`. Pin the installation target by serial, and explicitly disable IPv6 for this IPv4-only example:

```yaml
apiVersion: v1beta1
kind: AgentConfig
metadata:
  name: <cluster-name>
rendezvousIP: <server-ip>
hosts:
- hostname: <cluster-name>.<base-domain>
  interfaces:
  - name: <interface>
    macAddress: <mac>
  rootDeviceHints:
    serialNumber: "<disk-serial>"
  networkConfig:
    interfaces:
    - name: <interface>
      type: ethernet
      state: up
      mac-address: <mac>
      ipv4:
        enabled: true
        dhcp: false
        address:
        - ip: <server-ip>
          prefix-length: <prefix>
      ipv6:
        enabled: false
    dns-resolver:
      config:
        server:
        - <dns>
        - <dns2>
    routes:
      config:
      - destination: 0.0.0.0/0
        next-hop-address: <gateway>
        next-hop-interface: <interface>
```

For SNO, `rendezvousIP` is the node's own IPv4. Use exactly the same two resolvers that passed the preflight; do not mix a private-zone resolver with one that cannot resolve that zone.

Back up both files inside the protected installation directory so they will be included in Step 7's export:

```bash
(
  set -euo pipefail
  chmod 600 /root/ocp-prepare/install/{install-config,agent-config}.yaml
  cp /root/ocp-prepare/install/install-config.yaml /root/ocp-prepare/install/install-config.yaml.bak
  cp /root/ocp-prepare/install/agent-config.yaml /root/ocp-prepare/install/agent-config.yaml.bak
)
```

## Step 6 - Generate the PXE boot artifacts

Run the installer and check that all required artifacts and credentials exist before proceeding:

```bash
(
  set -euo pipefail
  openshift-install agent create pxe-files --dir /root/ocp-prepare/install
  for name in vmlinuz initrd.img rootfs.img; do
    file="/root/ocp-prepare/install/boot-artifacts/agent.x86_64-$name"
    test -s "$file"
    cp "$file" /root/
  done
  test -s /root/ocp-prepare/install/auth/kubeconfig
  test -s /root/ocp-prepare/install/auth/kubeadmin-password
  ls -lh /root/agent.x86_64-*
)
```

The expected files are:

```text
/root/ocp-prepare/install/boot-artifacts/agent.x86_64-vmlinuz
/root/ocp-prepare/install/boot-artifacts/agent.x86_64-initrd.img
/root/ocp-prepare/install/boot-artifacts/agent.x86_64-rootfs.img
/root/ocp-prepare/install/auth/kubeconfig
/root/ocp-prepare/install/auth/kubeadmin-password
```

A fresh attempt should use a clean installation working directory and newly generated matching artifacts. Preserve diagnostic evidence before removing files from a failed attempt.

## Step 7 - Save credentials and installer state off the rescue host

**Do not skip this step, regardless of the preparation path.** Rescue is temporary. Save the `auth/` directory, installer state, logs, and any configuration backups to your workstation before `kexec`. Treat the export as sensitive: it contains administrative credentials and may contain the pull secret. Do not commit it or attach it to a public issue.

On **rescue**, make an archive excluding the large boot artifacts:

```bash
(
  set -euo pipefail
  umask 077
  test -s /root/ocp-prepare/install/auth/kubeconfig
  test -s /root/ocp-prepare/install/auth/kubeadmin-password
  tar --exclude='./boot-artifacts' -C /root/ocp-prepare/install \
    -czf /root/ocp-install-backup.tar.gz .
  chmod 600 /root/ocp-install-backup.tar.gz
)
```

In a **separate workstation terminal**, copy and verify the export. This uses a new directory rather than overwriting your existing `~/.kube/config`:

```bash
(
  set -euo pipefail
  umask 077
  mkdir -p "$HOME/.kube"
  DEST=$(mktemp -d "$HOME/.kube/hetzner-sno.XXXXXX")
  scp 'root@<server-ip>:/root/ocp-install-backup.tar.gz' "$DEST/"
  tar -xzf "$DEST/ocp-install-backup.tar.gz" -C "$DEST"
  test -s "$DEST/auth/kubeconfig"
  test -s "$DEST/auth/kubeadmin-password"
  chmod 600 "$DEST/auth/"*
  printf 'Run these exports in your workstation shell:\n'
  printf 'export INSTALL_BACKUP=%q\n' "$DEST"
  printf 'export KUBECONFIG=%q\n' "$DEST/auth/kubeconfig"
)
```

Run the two printed export commands in that workstation shell. Confirm that you can read the saved password file locally; the API does not need to be running yet. Keep this terminal and the exported directory for Step 9. This tutorial does not provide a lost-credentials recovery procedure.

## Step 8 - kexec into the Agent installer

The Agent PXE assets separate the initrd and root filesystem. This workflow concatenates them into one buffer with zero-padding, retaining the original boot method. Linux documents concatenated archives and padding in its [initramfs buffer format](https://docs.kernel.org/driver-api/early-userspace/buffer-format.html); successful arithmetic alone does not validate a real RHCOS boot.

The padding is `4 + ((4 - (initrd_size % 4)) % 4)`. Build the combined image into a temporary file, and publish it only after both inputs have been copied successfully:

```bash
(
  set -euo pipefail
  cd /root
  INITRD=agent.x86_64-initrd.img
  ROOTFS=agent.x86_64-rootfs.img
  COMBINED=agent.x86_64-combinedinitrd.img
  test -s "$INITRD"
  test -s "$ROOTFS"
  temporary=$(mktemp ./combinedinitrd.XXXXXX)
  trap 'rm -f "$temporary"' EXIT
  INITRD_SIZE=$(wc -c < "$INITRD")
  PAD=$(( 4 + ((4 - (INITRD_SIZE % 4)) % 4) ))
  cat "$INITRD" > "$temporary"
  dd if=/dev/zero bs=1 count="$PAD" status=none >> "$temporary"
  cat "$ROOTFS" >> "$temporary"
  mv "$temporary" "$COMBINED"
)
```

Before proceeding, verify that Step 7 succeeded **on the workstation**, not just that a backup exists in rescue. The following block stops if loading the new kernel fails and asks for explicit confirmation before executing it:

```bash
(
  set -euo pipefail
  kexec -l /root/agent.x86_64-vmlinuz \
    --initrd=/root/agent.x86_64-combinedinitrd.img \
    --append='rw ignition.firstboot ignition.platform.id=metal'
  if ! read -r -p 'Credentials saved off-host? Type BOOT to leave rescue: ' confirmation || \
    [[ "$confirmation" != BOOT ]]; then
    kexec -u
    echo 'Boot cancelled; the loaded kernel was unloaded'
    exit 1
  fi
  sync
  kexec -e
)
```

Expect the SSH connection to close when the new kernel takes over. Do not immediately reset the server. Kernel loading can be refused by Secure Boot or lockdown policies; investigate the exact error or use standard boot media rather than bypassing those policies blindly.

## Step 9 - Verify the installation and browser login

Boot and image-pull times vary. Use observed progress and logs instead of treating a fixed number of minutes as proof of success or failure. Once RHCOS accepts SSH, connect as `core`:

```bash
ssh core@<server-ip>
```

SSH host keys change during reinstallation. Verify the new host-key fingerprint through a trusted channel such as KVM before removing a stale entry with `ssh-keygen -R '<server-ip>'`. Do not disable host-key checking globally.

On the **node**, inspect boot progress and the resolver path used by the installed system:

```bash
sudo journalctl -b -f
```

Use another node session for these snapshots:

```bash
sudo podman ps
systemctl --no-pager status kubelet crio
sudo ss -tlnp | grep ':6443'
getent ahostsv4 api.<cluster-name>.<base-domain>
getent ahostsv4 api-int.<cluster-name>.<base-domain>
getent ahostsv4 oauth-openshift.apps.<cluster-name>.<base-domain>
```

On the **workstation**, use the `KUBECONFIG` exported in Step 7. Initial API connection failures are expected until bootstrap has progressed:

```bash
oc get nodes
oc get clusterversion
oc get clusteroperators
```

The node should become `Ready` with the `control-plane,master,worker` roles. Wait for the cluster version to become available and finish progressing; investigate a failing cluster version instead of continuing:

```bash
(
  set -euo pipefail
  oc wait clusterversion/version --for=condition=Available=True --timeout=30m
  oc wait clusterversion/version --for=condition=Progressing=False --timeout=30m
  oc wait clusterversion/version --for=condition=Failing=False --timeout=30m
  oc wait nodes --all --for=condition=Ready=True --timeout=30m
)
```

Check a single snapshot of all cluster operators. This check fails for absent or unknown conditions, an empty response, and missing authentication, console, or ingress operators. Repeat it after waiting when operators are still converging:

```bash
(
  set -euo pipefail
  oc get clusteroperators -o json | python3 -c '
import json
import sys

required_conditions = {"Available": "True", "Progressing": "False", "Degraded": "False"}
operators = json.load(sys.stdin).get("items", [])
seen = set()
problems = []
for operator in operators:
    name = operator["metadata"]["name"]
    seen.add(name)
    conditions = {c["type"]: c["status"] for c in operator.get("status", {}).get("conditions", [])}
    for condition, expected in required_conditions.items():
        actual = conditions.get(condition, "Missing")
        if actual != expected:
            problems.append(f"{name}: {condition}={actual}, expected {expected}")
for name in sorted({"authentication", "console", "ingress"} - seen):
    problems.append(f"Missing cluster operator: {name}")
if not operators:
    problems.append("No cluster operators returned")
print("\n".join(problems) if problems else "All returned cluster operators have healthy conditions")
sys.exit(1 if problems else 0)
'
)
```

Operator status is not a browser-login test. Complete the following check as well, following Red Hat's [installation validation guidance](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/installation_overview/ocp-installation-overview).

### Check the console and OAuth from the workstation

Read the actual route names from the cluster:

```bash
oc whoami --show-console
oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}{"\n"}'
dig +short api.<cluster-name>.<base-domain> A
dig +short console-openshift-console.apps.<cluster-name>.<base-domain> A
dig +short oauth-openshift.apps.<cluster-name>.<base-domain> A
```

Open the exact console URL from `oc whoami --show-console`, not the bare IP. Handle the lab's certificate trust explicitly for both console and OAuth hostnames. Log in as `kubeadmin` using the saved password, complete the OAuth redirect, and confirm that the authenticated console loads. **Only a successful authenticated browser session closes the previously reported login failure.** Record the OpenShift version, preparation path, and result.

### If console or OAuth login fails

Collect evidence first; do not assume the cause is DNS. From the workstation:

```bash
oc describe clusteroperator authentication console ingress
oc get pods -n openshift-authentication -o wide
oc get pods -n openshift-ingress -o wide
oc get route -n openshift-authentication oauth-openshift -o yaml
oc logs -n openshift-authentication deployment/oauth-openshift --all-containers=true --tail=200
```

Separate normal DNS resolution from route/TLS connectivity with an **anonymous** health request. `--resolve` preserves the hostname and TLS SNI while selecting the server IP. `-k` below is for this diagnostic request only; it does not verify certificate trust and should not be used as the normal login procedure.

```bash
SERVER_IP='<server-ip>'
OAUTH_HOST=$(oc get route oauth-openshift -n openshift-authentication -o jsonpath='{.spec.host}')
curl --connect-timeout 10 --max-time 30 -ksS -o /dev/null \
  -w 'Normal DNS: HTTP %{http_code}\n' "https://$OAUTH_HOST/healthz"
curl --connect-timeout 10 --max-time 30 -ksS -o /dev/null \
  --resolve "$OAUTH_HOST:443:$SERVER_IP" \
  -w 'Selected IP: HTTP %{http_code}\n' "https://$OAUTH_HOST/healthz"
```

A successful selected-IP request with a failed normal request suggests a name-resolution or address-selection issue; it is not proof of successful authentication. If both fail, inspect ingress, firewall access, endpoints, and operator conditions. If both succeed but browser login fails, inspect the browser's exact error, certificate trust for both hostnames, and OAuth logs. Confirm that your browser's current public IP is allowed by Robot.

Node-level `getent` checks and workstation checks exercise different resolver paths. Operator conditions and OAuth pod logs provide additional evidence about in-cluster reachability. Keep the apps wildcard correct rather than adding isolated route records while leaving that wildcard broken. Sanitize logs and screenshots before sharing them; do not publish credentials, cookies, tokens, or the installation-state export.

If the node never becomes reachable, use KVM and inspect boot output, the NIC/MAC mapping, gateway, prefix, and resolver configuration. The absence of SSH alone does not identify the cause.

## Conclusion

The installation is prepared from the Rescue System and booted into RHCOS with `kexec`. Completion means a ready node, converged cluster version and operators, and successful authenticated console access, not merely an API that answers.

DNS for the API and application routes is a prerequisite, not a post-installation task. Review the firewall rules again when adding workloads, and maintain off-host backups because this single-node host remains a single point of failure.
